# dash-ota vs the alternatives

There are good OTA tools for React Native, and several of them do more than this page used to
give them credit for. Stallion signs its bundles with RSA/SHA-256 and verifies them on device.
hot-updater and Stallion both recover automatically from a bundle that fails to start. Expo's
`expo-updates` has opt-in code signing and its own error-recovery path.

So "we sign and they don't" is not the honest pitch. What is left, and what this page tries to
show, is narrower: where the signing key lives, what the update request itself proves, and what
the server can still do to you when it is hostile rather than merely wrong.

## Where the security rows actually differ

Signing is table stakes now. The differences are further down:

- **Where the signing key lives.** dash-ota's CLI signs and the backend never receives the key,
  so a breached distribution server has nothing to forge with. Stallion self-hosted lets you hold
  your own keys; its managed tier does not document where they live. With `expo-updates` it
  depends on whether you enabled code signing and who holds the certificate.
- **What the request proves.** Every dash-ota request is signed by a non-exportable key generated
  in the Secure Enclave or AndroidKeyStore, with a server-issued nonce and a timestamp. No other
  tool here authenticates the *device* rather than the *app*, so nothing else can tell a real
  install from a replayed or scripted one.
- **Whether the payload is readable.** dash-ota bundles are AES-256-GCM ciphertext. Everyone else
  ships plaintext JS over TLS to a bucket or CDN.
- **Who stops a bad release.** Every tool here rolls back on the device. dash-ota also pauses the
  release server-side once the failure rate crosses a threshold, so a bad bundle stops spreading
  without anyone being awake. That is the difference between recovering and containing.

None of this makes dash-ota strictly better. It makes it a different trade: more moving parts and
more to understand, in exchange for a server you do not have to trust.

## When *not* to choose dash-ota

- You want a managed dashboard, analytics and support, and are comfortable with a vendor →
  Stallion is less setup, has a free tier to 10K MAU, and signs its bundles too.
- You're all-in on Expo/EAS → `expo-updates` has opt-in code signing with an embedded X.509
  certificate and is far better integrated with that toolchain.
- You want the fastest path to a working self-hosted setup → `hot-updater` has an interactive
  `init`, adapters for Supabase, Cloudflare and S3, and a web console. dash-ota asks you to
  understand key custody before your first publish, on purpose.
- You need OTA on RN versions older than 0.79 / old architecture → dash-ota targets New Arch.

dash-ota's sweet spot is narrow and worth stating plainly: teams that must be able to say what
happens when the update server is compromised, and are willing to run a backend and understand
key custody to get there. If that sentence does not describe a requirement you actually have,
one of the others will get you shipping faster.
